能寫成 code，就不要用 judge

一個 failure mode，一個檢查，一個理由。

三個詞，先定義

Code evaluator：用程式檢查一個客觀規則，回傳 Pass/Fail 與理由。

LLM judge：用模型判斷需要詮釋的規則，例如語氣或同理心。

Proxy：用可觀察的替代訊號（例如關鍵字）代表你真正想量的東西。

決策順序

objective rule?
  │
  ├─ yes ──> code evaluator
  │
  └─ no
       │
       ▼
  needs interpretation?
       │
       ├─ yes ──> LLM judge
       └─ no  ──> add the missing data or policy

先把 code 的可能性用完，再考慮 judge。Judge 的成本、變異與驗證負擔都高得多。

看起來主觀，其實可以 code

Skill 的例子：判斷面試教練是否建議「一般性問題」（問典型行為，而不是具體事件），看起來需要語意理解；實務上用關鍵字 usually、typical、normally 就能抓到大部分。

重點不是「code 一定比較好」，而是「先問這條規則能不能寫成可觀察的條件」。

你的 8 個都能用 code 檢查，這不是巧合：你把 failure mode 定義成可觀察的行為了。Judge 留給語氣、同理心、說服力這類真的需要詮釋的東西。

Worked example：人數錯置

規則：使用者說 N 位，回覆卻說 M 人（M≠N）。

PARTY = re.compile(r"(\d+)\s*(?:位|人)")

def check_party_mismatch(trace):
    user, assistant = (turn["content"] for turn in trace["turns"])
    wanted = first_party(user)
    got = first_party(assistant)
    if wanted is None or got is None:
        return Result(trace["id"], True, "no party size in both turns")
    if wanted != got:
        return Result(trace["id"], False, f"user asked {wanted}, reply says {got}")
    return Result(trace["id"], True, f"party size matches ({wanted})")

練習：輪到你寫一個

在 toy/checks.py 加一個 check_special_omitted，並註冊進 CHECKS。規則：

  • 使用者提到 窗邊、無障礙、生日、花生過敏、兒童椅 其中之一。
  • 回覆必須提到它（或它的同義詞）。
  • 包場 不算，它是 routing failure，分開檢查。

先不要加同義詞，直接跑。你應該會看到三筆真陽性，還有幾筆因為「生日 vs 慶生」被誤判。

重點不是一次寫對

先寫一個粗的 proxy，跑在所有 traces 上，對照你的標註與 answer key，找出 false positive / false negative，再收緊規則。這就是 evaluator 的迭代。

什麼時候該放棄 code

  • 規則需要大量同義詞、例外、語氣判斷才能寫對。
  • 兩個人看同一筆會給不同答案，而且沒有客觀判準。
  • Proxy 的誤判率太高，且你無法用更精確的條件修正。

這時候才用 judge；用了之後還是要用 validate-evaluator 驗證它跟人類標籤的對齊。
