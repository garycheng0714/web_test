Lesson 0001 · Evals 基礎 · 約 20 分鐘

先看錯，再量測

Evals 不是儀表板；是一組你信得過的檢查。

三個詞，先定義

Trace：一次完整執行的紀錄——輸入、中間步驟、工具呼叫、最終輸出。

Eval：一個「這個行為是否成立」的檢查，回傳 Pass 或 Fail。不是 1–5 分。

Failure mode：產品會犯的一種可命名的錯，例如「把 7 人訂位排進 4 人桌」。

整門課都用 failure mode 當單位：一個名字，加一個可觀察的錯誤。

常見的錯誤順序

多數團隊從「容易量」的東西開始：延遲、token 數、一個 1–5 分的「helpfulness」，或憑想像寫的 LLM judge。這些是 vanity metrics：數字會動，但不告訴你產品哪裡壞。

順序反了的代價

如果你先寫 evaluator，你量的是「你猜的品質」。Error analysis 才把「猜」換成「觀察」。

  1. 收集 traces：真實或合成，重點是完整。
  2. Error analysis：人看 traces，替錯誤命名。
  3. 寫檢查：每個 failure mode 一個 evaluator。
  4. 驗證檢查：拿人類標籤比對，量 TPR/TNR。
  5. 回報：修正後的比率，加上不確定性。

這個迴圈會重跑。模型、prompt、功能一改，failure modes 就會換。

兩種 evaluator，先記一條規則

檢查的性質用什麼餐廳訂位助理的例子
客觀、可判定Code evaluator日期格式、人數上限、時段是否存在、JSON 欄位
需要詮釋LLM judge語氣是否合適、拒絕是否得體、建議是否切合情境

能用 code 就不要用 judge。 Judge 的成本、變異與驗證負擔都高得多。

為什麼是 binary

Pass/Fail 逼你先寫下邊界。1–5 分的 3 與 4 沒有共識，judge 會繼承那個噪音。

需要嚴重度時，用多個 binary 檢查（例如「事實錯誤」與「危險錯誤」），而不是一個 ordinal scale。
