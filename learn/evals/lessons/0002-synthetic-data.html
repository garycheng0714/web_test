Lesson 0002 · Evals 基礎 · 約 25 分鐘

沒有 traces，就先合成

你不是在造資料；你在覆蓋失敗空間。

三個詞，先定義

Synthetic data：不是真人輸入，而是為了覆蓋失敗空間而造的測試輸入。

Dimension：一個會影響行為的變化軸，例如 intent、party size、clarity。

Tuple：一組 dimension 值的組合，定義一個測試情境。

合成資料只解決「輸入從哪來」。它不產生人類標籤，也不取代真實 traces。

為什麼不要直接說「給我 20 個測試 query」

兩個原因，都會讓你測不到東西：

  • 沒有結構：模型會給你 happy path 與相似句型，覆蓋不到你預期會壞的地方。
  • 一步生成：tuple 和 query 一起寫，句型會更單調。分兩步，先想情境，再寫人話。

流程

dimensions
  │
  ▼
20 tuples (human-reviewed)
  │
  ▼
natural-language query  (separate step)
  │
  ▼
pipeline + full trace
  │
  ▼
quality filter
  1. 選 3 個維度，對準你預期會壞的地方，不是隨便的變化。
  2. 手寫 20 個 tuples，讓懂 domain 的人驗證真實性。
  3. 用 LLM 擴充 tuples，避免重複、讓值跨維度變化。
  4. 一次一個 tuple 寫成 query，這是獨立的一步。
  5. 過濾：不自然、對不上 tuple、彼此太像的就丟。
  6. 跑完整 pipeline，抓完整 traces；目標約 100 筆。

目標是 飽和：新 traces 不再帶出新的 failure mode。100 是粗略 heuristic，取決於系統複雜度。

玩具版：餐廳訂位助理

我們用三個維度：

Dimension值為什麼放進來
Intentbooking, modify, cancel, question, out_of_scope不同流程有不同的確認步驟
Party size2, 4, 7, 12小桌、大桌、需要特殊安排
Clarityclear, ambiguous, special_request缺資訊與特殊需求最容易壞

22 個 tuples 在 toy/tuples.json。玩具版用模板代替 LLM 生成 query，讓你離線跑；方法不變。

練習 1：先分清「真實」與「覆蓋」

這 22 個 tuple 沒有一個明顯是假的。它們是我刻意寫成 plausible 的；問題不是真假，而是「這個請求會不會真的進到這個 bot」。

但這個問題不能只看 tuple 回答。你需要三個 artifact：

Artifact回答什麼不要拿來
policybot 應該怎麼處理？推測實際行為
tuples要測哪些情境？判斷 bot 做得對不對
tracesbot 實際做了什麼？判斷輸入真不真實

下表是會引出 routing 問題的組合。沒有 policy 時，任何答案都是猜的：

Tuple要問的問題
t-020 12 人包場包場通常有最低消費或人數門檻，會走業務而不是訂位 bot 嗎？
t-004 / t-012 12 人大桌常要訂金或專人確認，bot 直接保留合理嗎？
t-018 無障礙真人會直接要求安排，還是只問「有沒有位子」？
t-006 生日只寫「生日」太模糊；真人會說「慶生」或「要蛋糕」嗎？

plausible ≠ 有覆蓋

句型自然，不代表測試有覆蓋。tuples 的價值在缺口，不在真假。

所以練習不是「標 2 個 routing tuple」，而是寫下你缺的資訊。在 NOTES.md 寫 2 條你需要的 policy 規則，再挑 2 個目前沒覆蓋的缺口：

  • 缺資訊的取消／改期（沒給姓名、電話、原訂位）
  • 情緒或客訴（「上次等很久」）
  • 錯字、注音、中英混雜
  • 矛盾限制（7 人，但 4 人桌也可以）
  • 超出範圍（寵物、停車、外送）

玩具 generator 的邊界

pipeline.py 目前只支援 intent / party / clarity 三軸；客訴、錯字、矛盾限制還沒有 schema。先把缺口記下來，不要硬塞進 tuple。

輸入設計先到這裡；Lesson 0003 才看 traces。之後真的要做 routing 時，再一起定 policy 與 generator 行為。

練習 2：產生 traces

在 repo 根目錄執行：

python3 learn/evals/toy/pipeline.py

它會讀 tuples.json，寫出 toy/traces.jsonl。每一筆長這樣：

{
  "id": "t-001-a",
  "tuple_id": "t-001",
  "turns": [
    {"role": "user", "content": "你好，我想訂週五 19:00，2 位。"},
    {"role": "assistant", "content": "好的，已為您保留週五 19:15 的 2 人桌。..."}
  ],
  "meta": {"intent": "booking", "clarity": "clear", "party": 2, ...}
}

檢查點：

  • wc -l learn/evals/toy/traces.jsonl 是 44（你加了 tuple 就會更多）。
  • 每筆都有 id、tuple_id、turns、meta。
  • 你還沒有開始標註，也還沒有下結論。

先不要分析 failure

打開 traces 你會立刻看到幾個明顯的錯。先忍住。Lesson 0003 才做 error discovery；現在只要確認資料形狀與覆蓋範圍。

Spoiler 警告

toy/answer-key.json 與 pipeline.py 的 SPOILER 段是植入錯誤的答案。Lesson 0003 結束前不要打開，否則 error discovery 會變成對答案。
