Lesson 0007 · Evals 基礎 · 約 30 分鐘

審一份 eval pipeline

你現在是 auditor：找最該修的問題，不是把所有東西重寫。

Audit 不是 checklist

Checklist 只告訴你要看什麼；audit 要你打開 artifacts、判斷問題是否存在、排 impact。沒有打開檔案的 audit，只是 generic advice。

最常見的 anti-pattern：跑完六個區域，每區寫一句「建議補齊」，但沒有指出哪個檔案、哪個數字、哪個決策會被影響。

六個區域

Area要看什麼常見 finding
Error Analysis有 traces、failure categories、review notes？沒做 error analysis 就寫 evaluator
Evaluator DesignBinary？一個 mode 一個 check？code 優先？Likert、holistic judge、用 judge 檢查 schema
Judge ValidationTPR/TNR？splits？沒有 leakage？Judge 沒驗證、用 raw accuracy、用 dev/test 當 few-shot
Human ReviewDomain expert？看完整 trace？UI 可讀？外包給不懂 domain 的人、只看最終輸出、raw JSON
Labeled Data~100 traces？50／50？抽樣策略？資料太少、只抽常見案例、沒有 random sample
Pipeline Hygiene改版後有重跑？judge 有重驗證？模型有 pin？Error analysis 過期、evaluator set-and-forget

Report 格式

### [Problem Title]
**Area:** [1–6]
**Status:** Problem exists / OK / Cannot determine
[1–2 sentences：具體發生什麼]
**Fix:** [concrete action + skill]

依 impact 排序：會讓決策錯的最前面，polish 最後。

Worked example

這個 workspace 裡的一個真實 finding：

Judge 沒有被驗證，卻被當成對齊

Area: Judge Validation
Status: Problem exists

judge_tone.md 只在 5 筆上試跑，TPR／TNR = 1.00，但沒有 train／dev／test split，也沒有 CI。5 筆的 1.00 不能支持「judge 可用」。

Fix: 補到 ~50 Pass + 50 Fail，切 train／dev／test，量 TPR／TNR 與 bootstrap CI；用 validate-evaluator。

規則：

  • 每個 finding 都要指出具體檔案或數字；不要寫 generic advice。
  • 沒問題的區域寫 OK；資料不足就寫 Cannot determine，不要硬掰。
  • 依 impact 排序：決策風險最高的放前面。

怎麼排 impact

訊號Impact
沒有 failure modes 就寫 evaluator最高：整條 pipeline 量錯東西
Judge 沒驗證就被當成對齊高：決策會被假數字帶走
已知 failure mode 沒有 evaluator中：覆蓋缺口
UI 不好用、檔名不一致低：polish

七課之後

你現在有一套可重複的流程：traces → error analysis → evaluator → validation → corrected rate。下一步是把同樣的流程帶到真實專案：

  • 用真實 traces 重跑 error discovery；合成資料只補缺口。
  • 把 judge 的 TPR／TNR 與 CI 放進決策文件，不要只報單點。
  • 模型、prompt、功能一改，就重跑 error analysis 與 validation。
  • 需要時再加 production monitoring、CI gate、RAG 專項評測。
