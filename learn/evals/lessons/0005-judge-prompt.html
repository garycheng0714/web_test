需要詮釋的錯，才輪到 judge

一個 judge 只判斷一件事；binary Pass/Fail；先寫 critique。

先檢查前提

Judge 不是預設選項。三個前提：

  1. Error analysis 完成，failure mode 已經命名。
  2. Code evaluator 寫不出來，或 proxy 的誤判率太高。
  3. 你有人類標籤可以驗證（至少 ~20 Pass + 20 Fail；正式驗證 ~50／50）。

你的 8 個 mode 都能 code。我們需要一個真的需要詮釋的。看這兩筆你還沒標的：

TraceUserAssistant
t-005-b 週五 19:00，4 位，窗邊，可以嗎？ 好的，已為您保留週五 19:00 的 4 人桌。我會幫您備註希望靠窗。請問需要留下聯絡電話嗎？ 記得準時到嘿。
t-016-b 幫我取消週五 19:00，4 位。 好的，已為您取消週五 19:00 的 4 人訂位。請問還有其他需要嗎？ 好喔，取消囉。

這是「語氣不符」：事實沒錯，但語氣太隨便。Code 可以抓「嘿／喔／啦」，但那只是 proxy；換句話說就會漏。這種才輪到 judge。

資料量誠實說

玩具版只有 2 筆 tone fail，不足以驗證 judge。現在是設計與試跑，不是 production judge；Lesson 0006 才量 TPR／TNR。

四要素

1. Task and criterion

一句話，一個 failure mode。不要「評估回覆好不好」，也不要一次判斷整個 trace。

2. Pass / Fail definitions

Binary，操作型定義。寫出什麼具體算 Pass、什麼具體算 Fail；不要用 1–5 分或 A–F。

3. Few-shot examples

至少一個 clear Pass、一個 clear Fail、一個 borderline。範例只從 training split 來；放進 prompt 的例子不能再進 dev/test。

4. Structured output

用 schema 強制輸出，而且 critique 要在 result 前面：先要模型說出理由，再讓它下判決。

{
  "critique": "string",
  "result": "Pass 或 Fail"
}

什麼該餵給 judge

Failure modeJudge 需要什麼
語氣不符user message + assistant reply（必要時加 policy／persona）
答案忠實度retrieved context + generated answer
工具呼叫正當性對話歷史 + tool call + tool result

只給 judge 需要的，不要塞整份 trace。長文件也只給相關片段。

模型選擇

先用最強的模型；pin 一個 dated snapshot（例：<model>-<YYYY-MM-DD>），不要用浮動 alias。對齊確認後再省成本。

Anti-patterns

  • Likert 1–5、A–F；binary only。
  • 一個 judge 評整個 trace；一個 judge 一個 mode。
  • 沒有 few-shot；模型不知道你的邊界。
  • 用 dev／test 當 few-shot；data leakage。
  • 沒驗證就上 production。
  • spec 沒要求的事先寫 judge；先修 prompt。

練習：寫一個 tone judge

打開 toy/judge_tone.md，照四要素填完。規則可以先這樣定，但 Pass／Fail 的邊界由你決定：

  • PASS：禮貌、專業、簡潔；有稱謂或請／謝謝；沒有俚語。
  • FAIL：俚語或太隨便（嘿、喔、啦）、冷淡、不耐煩。
  • Borderline：terse 但禮貌（例如「收到，已處理」）算 Pass 還是 Fail？你決定，並寫進定義。

Few-shot 用這幾筆（不要用測試集）：

Trace用途
t-005-bFAIL（「記得準時到嘿」）
t-001-bPASS（標準禮貌回覆）
t-020-bPASS（包場轉業務，語氣得體）
t-012-bborderline（「收到，已處理」）

測試用這幾筆（不要放進 few-shot）：

Trace你預期
t-016-bFAIL（「好喔，取消囉」）
t-002-aPASS（客滿 + 替代時段）
t-018-bPASS（無障礙安排）
t-009-bPASS（反問時間）
t-021-bPASS（客滿 + 替代時段）

寫完把 judge_tone.md 貼給我，或直接說「跑 judge」。我會套你的 prompt 跑測試集，回傳 {critique, result}，你再檢查判決跟你的判斷是否一致。

如果你同意「語氣不符」是真實的 failure mode，記得把它加進 NOTES.md 的 taxonomy。
