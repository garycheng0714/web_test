Lesson 0003 · Evals 基礎 · 約 35 分鐘

先命名錯誤，再談量測

Error discovery 的產出不是分數，是一份 failure mode 清單。

三個詞，先定義

Error analysis：人看 traces、替錯誤命名，產出 failure mode 清單。

Failure mode：一種可命名的錯，附一個可觀察的例子。

Taxonomy：把相似的錯收斂成同一個名字的清單。

為什麼先求多樣性，不是頻率

這一步的目標是「發現未知的失敗類型」，不是「估計發生率」。所以你會刻意抽 cluster 代表 + 隨機樣本，而不是只看最常出現的 happy path。

44 筆不多，先標 20–25 筆，涵蓋不同 intent、party size、clarity。不要只讀前 20 筆。

開始之前

把你 Lesson 0001 的 5 個猜測貼到 NOTES.md 的「Lesson 0001 guesses」。標完再回來對照，不要現在看答案。

跑 review app

python3 learn/evals/toy/review.py

打開 http://localhost:8765。左邊是 trace，右邊是 failure modes 與進度。每改一次就自動存到 toy/annotations.json。

若 8765 被占用，加一個埠號：python3 learn/evals/toy/review.py 8766。

怎麼標

  1. 先讀 user message，記住 party、day、time、special。
  2. 再讀 assistant reply，逐項對照：數字、日期、時段、特殊需求、語氣。
  3. 同一個 tuple 的 a／b 兩筆要一起看；paired diff 的差異通常就是缺陷。
  4. 有錯就寫 note，引用原文；給它一個短 mode 名稱。
  5. 一筆有兩個錯，用「、」分隔 mode（例：人數錯置、缺少確認）。
  6. 不確定是不是錯，先寫下來。Lesson 0004 才決定要不要把它變成 evaluator。

不要做的事

不要用 1–5 分、不要用「好／不好」、不要先想 evaluator。你現在只做一件事：把錯命名。

標完之後

看右邊的 failure modes：

  • 合併同義詞（「人數錯」與「人數錯置」算同一個）。
  • 挑 3–5 個最重要的 mode，在 NOTES.md 寫定義。
  • 定義要可觀察，例如：「使用者說 N 人，回覆保留 M 人（M≠N）」。
  • 每個 mode 留一個代表 trace id。

格式可以照這個：

## Lesson 0003 failure modes
**人數錯置**: 使用者說 N 人，回覆保留 M 人（M≠N）。
- 例子：t-004-a
- 為什麼重要：人數錯會導致現場無法入座。

對照你的猜測

回到 Lesson 0001 的 5 個猜測：

  • 你猜中幾個？
  • 哪些是你沒猜到、但 traces 裡真的出現的？
  • 哪些你猜了、但 traces 裡沒有？

這個落差就是 error analysis 的價值：它把「你以為的品質」換成「實際的失敗」。

Spoiler：對答案

寫完 3–5 個定義後，再打開 toy/answer-key.json。它記錄了植入的 defect。只做兩件事：

  • 哪些植入的 mode 你抓到、哪些漏了？
  • 你命名的 mode 有沒有比答案更好的？答案不是聖經。

什麼時候算飽和

新 traces 不再帶出新的 failure mode。44 筆的玩具資料很容易飽和；真實系統通常要 ~100 筆。

飽和不是「每個 mode 都出現 50 次」，而是「新模式不再出現」。

小測驗

1. Error discovery 先求什麼？

2. 什麼時候算飽和？

3. 一筆 trace 同時有兩個錯，應該怎麼記？
