Spec 模板速查

`to-spec` 產出的檔案就長這樣。搭配第二課 0002-to-spec。

七個區塊

區塊放什麼
Problem Statement使用者視角的問題本身。
Solution使用者視角的解法。
User Stories很長的編號清單：As an <actor>, I want <feature>, so that <benefit>，涵蓋所有面向。
Implementation Decisions要建/改哪些 module、介面、技術決策、schema、API 契約、互動。不寫檔名與程式碼片段（會過時）。
Testing Decisions什麼是好測試（只驗外部行為）、哪些 module 要測、可參考的既有測試。
Out of Scope明確不做的事。
Further Notes其他補充。

兩條硬規則

  • 不要寫檔名或程式碼片段——它們很快過時。唯一例外：原型產出的片段若比文字更精確地編碼了一個決策（狀態機、reducer、schema、型別形狀），可內嵌並註明來自原型，且只留關鍵部分。
  • spec vs ticket：spec 是跨 session 的工作，由多張 ticket 組成；ticket 是單一 session 的工作範圍。一張 ticket 不該需要 handoff。

產出位置（本 repo）

.scratch/<feature-slug>/spec.md

發佈後套上 ready-for-agent 標籤（見 MISSION.md 旁的 docs/agents/triage-labels.md）。
