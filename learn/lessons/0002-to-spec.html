to-spec：把對話收斂成規格

這一課只教你一件事：說出 spec 七個區塊各放什麼，並在寫之前先決定「在哪個 seam 測」。

學完你能做到

看著我們的 agent 功能，你能講出 spec 每一區要填什麼，並指出要在哪裡測試它。

先分清 spec 與 ticket

範圍是否要 handoff
spec跨多個 session 的工作要；本身由多張 ticket 組成
ticket單一 session 的工作不用；需要 handoff 代表票太大，要再切

這就是為什麼主流程在「多 session 的大工作」時走 to-spec → to-tickets。

to-spec 的流程

1. 探索 codebase（用 CONTEXT.md 的詞彙、尊重相關 ADR） 2. 勾勒測試 seam（優先用既有 seam；最少、最高最好） 3. 與使用者確認這些 seam ← 不能跳過 4. 用模板寫 spec → 發佈到 tracker，套 ready-for-agent

seam 是「你測試與觀察行為的公開邊界」。規則：測試只立在事先講好的 seam，不測內部實作。

檢索練習

Q1. spec 與 ticket 的核心差別是？

  • 正確。spec 跨多個 session，由多張單一 session 的 ticket 組成。

Q2. 寫 spec 之前，to-spec 要求先做什麼？

  • 正確。先勾勒 seam 並與使用者確認，才能確保測試立在對的邊界。

Q3. Implementation Decisions 不該包含下列何者？

  • 正確。檔名與程式碼很快過時；改寫成 module 與介面層級的決策。
